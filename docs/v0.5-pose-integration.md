# v0.5 — joining the Flutter app to the pose rule engine

**Status: design only. Nothing here is implemented.**

v0.1 ships a Flutter app (`app/`) that runs structured sessions with an
anticipatory coach and no AI. `src/boxing_coach/` is a Python pose-analysis
engine: MediaPipe pose in, deterministic boxing rules out, `RoundAnalysis` as
the result. They do not talk to each other yet.

v0.5 is the version where they meet, and it is the version the spec calls the
MVP:

> **v0.5:** Add recording and pose-only analysis. Ship the "MVP" listed above.
> This validates the core value proposition.

Concretely that means: record the technical rounds, run pose estimation on
device, run the rules over the keypoints, and speak the result in the rest
period — with no API model anywhere (`PoseOnlyAdapter` only, per the spec).

This document covers four things: how pose capture works inside Flutter, where
the rule engine should run, how data crosses between the two halves, and the
order to build it in.

---

## 1. On-device pose capture in Flutter

### The shape of the flow

The spec's recording flow is not real-time. It is:

```
round start → record → round end → analyse during rest → speak before next round
```

That is a gift, and the architecture should take it. Nothing has to keep up with
the camera at 60fps live; the analysis has a whole rest period (30–90s in v0.1's
configurations) to process a 2–3 minute clip. **Record to a file, then run pose
estimation over the file.** This avoids the hardest part of on-device vision —
sustained real-time throughput with a UI on top — for no loss in product value,
because the spec has already ruled out real-time in-round coaching:

> **Not attempted:** Real-time in-round coaching (latency and UX both wrong).

### Components

| Job | Choice |
| --- | --- |
| Camera preview, permissions, recording | `camera` plugin (first-party Flutter) |
| Pose estimation | **MediaPipe Tasks Vision — Pose Landmarker**, `VIDEO` running mode, over the recorded file |
| Android binding | `com.google.mediapipe:tasks-vision` |
| iOS binding | `MediaPipeTasksVision` (CocoaPods) |
| Model asset | `pose_landmarker_lite.task` (~6 MB) shipped in the app bundle; `_full` (~9 MB) as a device-tier upgrade |
| Frame decode | Android `MediaMetadataRetriever` / `MediaCodec`; iOS `AVAssetReader` |
| Dart ↔ native | A small federated plugin in `app/packages/pose_landmarker/` |

**Write the plugin rather than depending on a community wrapper.** The surface
needed is tiny — one method — and the community MediaPipe plugins have a history
of lagging the native SDKs and of exposing only `IMAGE`/`LIVE_STREAM` modes.
The whole Dart API is:

```dart
abstract class PoseLandmarker {
  /// Runs pose estimation over a recorded clip.
  ///
  /// Emits progress so the rest-period UI can show something moving, and
  /// returns the sequence the rules consume.
  Stream<PoseEstimationProgress> estimate(
    String videoPath, {
    Duration sampleEvery = const Duration(milliseconds: 33),
    PoseModel model = PoseModel.lite,
  });
}
```

Everything native stays behind it: decoding, timestamping, model loading,
delegate selection (GPU where available, CPU fallback).

### Landmark compatibility with the Python engine

The Python estimator uses the **legacy** `mp.solutions.Pose` API — `pyproject.toml`
pins `mediapipe<0.10.30` precisely because that API was removed afterwards. The
mobile SDKs only offer the **Tasks** API. This is fine, and it is worth being
precise about why:

- Both emit the **same 33-landmark topology with the same indices**, which is
  what `domain/landmarks.py` encodes (`NOSE = 0`, `LEFT_SHOULDER = 11`, …). The
  `Landmark` enum maps to Tasks output directly, no remapping table.
- Both emit normalised `x`/`y` in roughly `[0, 1]` with y increasing downward —
  the convention documented in `landmarks.py` and relied on by every rule.
- Two differences to handle explicitly:
  - **`visibility` vs `presence`.** Tasks exposes both; legacy exposes only
    `visibility`. Populate `Keypoint.visibility` from Tasks' `visibility` and
    drop `presence`, so the field means the same thing on both sides.
  - **`z`.** Tasks normalises depth roughly to the same scale as `x`, with the
    hip midpoint as origin. Legacy's `z` is similar but not identical. Since
    monocular depth is unreliable anyway (the spec says so at length), **treat
    `z` as unusable in v0.5** and do not ship any rule that depends on it —
    which means `hip_rotation` stays off until multi-view 3D at v2.

One task that pays for itself early: capture the same clip through both APIs and
diff the resulting `PoseSequence`s. If they agree within noise, every threshold
calibrated on desktop transfers to the phone. If they do not, we want to know
that before the rules ship, not after.

### Sampling rate

`MediaPipePoseEstimator` defaults to `sample_every_ms=40` and its docstring
already makes the argument: a jab lasts ~100–150 ms, so 100 ms sampling smears
exactly the retraction timing the guard-return rule measures. Record at **60fps
where the device supports it** and sample every frame (~16 ms) for technical
rounds; fall back to 30fps/33 ms. A 3-minute round at 33 ms is ~5,400 frames ×
17 landmarks — a few hundred KB in memory, trivial.

### Cost of the analysis pass

Rough budget for a 3-minute round on a mid-range phone: pose landmarker lite on
GPU runs comfortably faster than real time on a decoded frame stream, so expect
the pass to finish well inside a 60-second rest. It must be measured, not
assumed — that measurement is a deliverable of stage 0.3 below, and if it does
not fit, the lever is sampling rate, not architecture.

## 2. The key decision: where does the rule engine run?

Three options. The recommendation is A.

### A. Port the rule engine to Dart *(recommended)*

Everything runs in one process: capture → keypoints → rules → coach.

**For:**

- It is the only option that satisfies what the spec already decided. On-device
  analysis is what makes the free tier free ("the phone does pose estimation
  locally, at near-zero marginal cost — which makes a sustainable free tier")
  and what makes the privacy claim true. Both are undermined the moment a round
  needs a server to be analysed.
- It works in a gym basement with no signal. Sessions happen where they happen.
- No IPC, no serialisation, no round-trip inside a 60-second rest window.
- The engine is a good porting target: ~2,200 lines, no I/O, no framework, and
  numpy used for array arithmetic rather than anything exotic. The pieces v0.5
  actually needs are smaller still (see the scope note below).
- The seams are already right. `Rule`, `AnalysisContext`, `StyleProfile` and
  `VisionAnalysisAdapter` port across as-is; `RuleEngine.run` is 15 lines.

**Against:**

- Two implementations of the same logic, and the rules are still moving — the
  recent commit history is threshold corrections found on real footage. Drift is
  the real risk, not translation difficulty.
- numpy has to become explicit loops or a small vector helper. `geometry.py` and
  `features.py` are where the work is.

**How to defuse the drift risk — cross-language golden fixtures.** This is the
part that has to exist for option A to be safe:

1. Define a JSON encoding of `PoseSequence` (§3) plus a JSON encoding of
   `RoundAnalysis`.
2. Add a Python CLI (`boxing-coach fixtures --emit`) that writes, for each
   `tests/fixtures.py` scenario and each real clip we have, a pair of
   `{input.json, expected.json}` into `fixtures/golden/`.
3. Both test suites read the same files. Python asserts it still produces
   `expected.json`; Dart asserts it produces the same.
4. Any threshold change is made in Python, regenerates the goldens, and the Dart
   suite goes red until it is ported. Drift becomes a failing test rather than a
   discovered surprise.

**Keep Python as the reference implementation and the lab.** It stays the place
thresholds are calibrated (it has the CLI, real video processing, and
`rendering/stills.py` for eyeballing what a rule fired on). The Dart port is the
shipping runtime, not the source of truth.

**Scope the port to what v0.5 ships.** The spec's v0.5 rule list is: guard
return, punch retraction, basic stance, head movement presence. That is:

| Port now | Leave in Python for now |
| --- | --- |
| `geometry.py`, `features.py` (`body_scale`, `PunchDetector`) | `hip_rotation` (needs `z` — blocked until v2 anyway) |
| `rules/guard_return.py`, `rules/hands_up.py` | `rules/school_adherence.py`, `schools.py`, `round_profile.py` |
| `rules/head_movement.py`, `rules/footwork.py` | `punch_classifier.py` (only needed for punch-mix reporting) |
| `rule.py`, `engine.py`, `context.py`, `style.py`, `style_profiles.py` | `rendering/stills.py` (see §3) |
| `adapters/pose_only.py` synthesis | |

That is roughly half the engine, and the half with the fewest moving parts.

### B. Run the Python engine server-side

Phone extracts keypoints, POSTs a few KB, gets `RoundAnalysis` back.

**For:** no port, one implementation, thresholds updatable without an app
release — genuinely valuable while the rules are still being calibrated.

**Against:** it contradicts the free-tier economics and the offline promise;
it needs hosting, auth and an ops story for a proof-of-concept-stage product;
and the failure mode is the worst kind — the app silently stops coaching when
the wifi is bad, in the middle of a session. Bandwidth is *not* the objection
(a round is a few KB), the dependency is.

**Where it is genuinely useful:** as a *private beta calibration channel*, not
as the product path. During stage 0.35 below, the phone uploads (with explicit
consent) the pose JSON of rounds we are calibrating against, and the Python
engine is run over them offline. Same code path as the golden-fixture harness,
no server in the shipping product.

### C. Bundle Python via FFI or an embedded interpreter

**Rejected.** An embedded CPython plus numpy for arm64 on both platforms adds
tens of megabytes, a fragile build, real startup cost, and an iOS toolchain
story nobody wants to maintain — to run 2,200 lines of arithmetic that Dart can
do natively. There is no upside that option A does not already have. The one
argument for it — "one implementation" — is better served by the golden-fixture
harness, which costs a fraction as much.

### Recommendation

**Port to Dart (A), scoped to the v0.5 rules, behind a cross-language golden
fixture suite, with Python retained as the reference implementation and the
calibration lab.** Use B's transport only as a consented calibration upload
during beta, never as the analysis path in the shipping app.

## 3. The data bridge

### 3.1 `PoseSequence` — the interchange type

The Dart mirror stays structurally identical to `domain/pose.py`, because
everything downstream is a direct port:

```dart
class Keypoint { final double x, y, z, visibility; }
class PoseFrame { final int index; final double timestampMs;
                  final Map<Landmark, Keypoint> keypoints; }
class PoseSequence { final List<PoseFrame> frames; final double fps;
                     final String source; final Map<String, Object?> meta; }
```

`Landmark` is an enum whose values are the MediaPipe indices, matching
`domain/landmarks.py` exactly.

JSON encoding, used by the golden fixtures and (during beta) the calibration
upload — landmark index as key, fixed field order, floats rounded to 4 decimals:

```json
{
  "fps": 30.0,
  "source": "pixel-8/technical-round-3",
  "meta": {"model": "pose_landmarker_lite", "sampleEveryMs": 33},
  "frames": [
    {"i": 0, "t": 0.0, "kp": {"11": [0.4212, 0.3130, -0.11, 0.99], ...}}
  ]
}
```

At 4 decimals × 17 landmarks × ~5,400 frames a round is a few hundred KB of
JSON, or a few tens of KB gzipped — still nothing, and it keeps the fixtures
diffable, which matters more than the bytes.

### 3.2 `DrillContext` — v0.1 already computes it

`DrillContext(stance, style, school, focus, notes)` is exactly what the running
session knows. The v0.1 `SessionSegment` carries the phase, the theme, and the
`Exercise` with its weighted categories; `focus` is a set of free-form tags and
the category keys were aligned to the Python enum in v0.1 for precisely this
reason. So:

```dart
DrillContext(
  stance: profile.stance,                      // user profile, new in v0.5
  style: profile.style,                        // 'high guard' default
  school: null,                                // v2
  focus: segment.exercise.categoryWeights.keys // e.g. {'offence_jab', 'defence'}
      .map((c) => c.key).toSet(),
  notes: segment.note ?? '',
);
```

`Rule.applies_to` and `StyleProfile.enables` then gate the rule set per round for
free — a jab drill runs the guard-return rule, a footwork drill does not have to.
That machinery already exists in Python; the port inherits it.

### 3.3 `RoundAnalysis` — back into the coach

The output types (`Observation`, `Correction`, `FlaggedMoment`, `RoundMetrics`)
port field-for-field. What is new is delivering them, and that needs one change
to the v0.1 engine.

**v0.1's cue script is static** — `CueScheduler` computes the whole session's
cues up front, which is what makes the coach deterministic and testable. Analysis
results arrive mid-session and cannot be precomputed. The clean way to admit
them without giving up determinism:

```dart
/// Injects a cue produced during the session (analysis feedback, a user
/// prompt). Scheduled cues still own their slots; an injected cue waits for
/// the next gap rather than talking over a round call.
void enqueue(ScheduledCue cue, {required int segmentIndex});
```

The scheduler stays the authority on *when* the coach may speak; the analysis
supplies *what*. The rest-period script then becomes:

| Offset into rest | Cue |
| --- | --- |
| 0s | end bell, "Rest. Breathe." *(v0.1, unchanged)* |
| ~8s | `analysis.overall_summary` *(injected when ready)* |
| ~16s | `correction_priorities.first.description` *(injected)* |
| rest − 30s | next-round preview *(v0.1, unchanged)* |
| rest − 10s | "Ten seconds. Hands up." *(v0.1, unchanged)* |

If analysis is not finished by the preview slot, it is dropped for that round
rather than delaying the session — a late correction is worse than no correction,
and the observation is still in the round review.

Two user-instigated prompts from the spec's coach behaviour also land here:
**"Camera check — can you see yourself in frame?"** before the first technical
round (a live pose check confirming the full body is visible: it is the mitigation
for the spec's risk #3, and it needs the landmarker running in `LIVE_STREAM` mode
for a few seconds), and **"How did that feel? 1-5"** after it.

### 3.4 Flagged moments and stills

`rendering/stills.py` re-opens the video, draws the skeleton on the frame at a
correction's timestamp, and circles the at-fault landmarks. On mobile the
equivalent is: seek the local clip to `example_timestamp_ms`, and draw the
skeleton in a Flutter `CustomPainter` over the video frame — no port needed, and
it is better than a baked PNG because the user can scrub around the moment.

Note the spec's own caution when this data later reaches a model: send *clean*
frames plus pose-as-text, not annotated pixels. That is a v0.8 concern, but it
means the annotation must stay a display layer, never baked into stored frames.

### 3.5 Persistence

v0.1 stores nothing but slider positions. v0.5 needs the spec's SQLite schema —
`session_instances`, `session_rounds`, `round_analyses`, `round_corrections`,
`round_observations` — because session history and the weekly balance view are
both on the MVP list. `sqflite` on both platforms; `SessionPlan` already produces
everything `session_rounds` wants (phase, exercise, duration, rest, theme).

Video retention follows the spec's open question 2: **keep clips 7 days, then
delete unless explicitly saved; analysis persists.** Implement the deletion sweep
at the same time as the writing — a retention policy added later is a retention
policy that never ships.

## 4. Delivery plan

Five stages. Each is shippable to a single real user (the athlete this is being
built for) and each answers one question before the next begins. The ordering
principle is the spec's risk #1: *the vision analysis quality is the entire
product's credibility*, so no user-facing correction is spoken until the rules
have been checked against footage where the answer is known.

### 0.2 — Recording, no analysis

Camera permissions, a pre-flight camera-check screen with framing guidance, auto
record on technical round start, auto stop on round end, local storage with the
7-day sweep, and a review screen to scrub the clip.

*Question answered:* can a person actually get themselves in frame in a living
room? The spec calls camera setup a top-three risk and it is entirely a UX
problem — worth isolating from everything technical.

*Ships:* recording + review. No claims.

### 0.3 — Pose on device, no coaching

Bundle the model, add the `pose_landmarker` plugin, run it over the recorded clip
during the rest period. Surface only mechanical facts: frames analysed, seconds
taken, percentage of frames with a full body visible, and a skeleton overlay on
the review screen.

*Question answered:* does pose estimation fit in the rest window on the target
device, and is the skeleton good enough on real footage in real lighting?

*Ships:* an honest "we can see you" indicator, which doubles as the camera check.

### 0.35 — Parity and calibration (internal only)

Export `PoseSequence` JSON from the phone. Run the Python engine over it on a
desktop. Compare against hand-labelled footage: for each round, did guard-return
fire when a coach would say the hand dropped?

Build the golden fixture harness here (§2A) and freeze the JSON schema. Tune
thresholds in Python, where the CLI and the annotated stills already exist.

*Question answered:* are the thresholds right on this athlete's footage, and does
Tasks-API pose agree with legacy-API pose?

*Ships:* nothing to the user. This is the stage that protects credibility, and
skipping it is how a product ends up confidently wrong.

### 0.4 — The Dart rule engine, in shadow mode

Port, rule by rule, each landing green against the goldens: geometry →
`body_scale` → `PunchDetector` → `guard_return` → `hands_up` → `head_movement` →
`footwork` → `PoseOnlyAdapter` synthesis.

Run it in the app after every technical round and **log the result without
speaking it**. Compare a week of shadow output against what the athlete says
happened.

*Question answered:* does the ported engine agree with the reference on real
sessions, and does its output read as true to the person who was in the round?

### 0.5 — Turn the coaching on

Speak the summary and the top correction in the rest period. Add the round review
screen with flagged moments. Add the SQLite history and the weekly category
balance view (v0.1's weighted-minutes model, rolled up across sessions). This is
the spec's MVP.

*Start narrow.* Guard return and punch retraction first — they are the most
reliable and the easiest to feel the truth of. Add head-movement presence and
footwork presence once the first two have gone a fortnight without a wrong call.
The spec's instruction is explicit: *"start with fewer, more reliable
observations rather than trying to catch everything."*

### Held back deliberately

| Not in v0.5 | Why |
| --- | --- |
| Any API model — phrasing, summaries, adjudication | The spec: "v0.5 ships with none of it." That is v0.8. |
| `hip_rotation` and any rotation/weight-transfer rule | Depends on `z`; monocular depth is the least reliable output. v2. |
| Style and school coaching (`school_adherence`, `schools.py`) | v2, and it needs a real coach's input to be worth shipping. |
| Multi-camera anything | v2, and gated on a two-phone auto-calibration prototype. |
| Real-time in-round analysis | Explicitly not attempted, in the spec and here. |

## 5. Open questions to settle before starting

1. **Tasks vs legacy landmark parity.** Cheap to measure, and everything
   calibrated on desktop rides on the answer. Measure in 0.3.
2. **Analysis wall-clock on the target device.** If a 3-minute round at 33 ms
   sampling does not fit in a 60-second rest, the lever is sampling rate or
   analysing only a window of the round — decide with a number, in 0.3.
3. **Where the stance comes from.** `DrillContext.stance` defaults to orthodox
   and every rule that cares about lead vs rear hand depends on it. A user
   profile field is the obvious answer; detecting it from the pose is a nice
   touch and a needless dependency.
4. **What "punch retraction" is called in the UI.** The spec lists guard return
   and punch retraction as separate v1 detections, but `guard_return.py` covers
   both mechanisms. Decide whether they are one observation or two before the
   copy is written.
5. **Beta upload consent.** The calibration channel in 0.35 uploads pose data —
   a few KB, no pixels — from a real person's training. It needs an explicit,
   revocable opt-in even in a beta of one.
